# AI生成物判定プロダクト - 技術設計書

作成日: 2026-05-05
作成者: 開発部

---

## 1. プロダクト概要

ユーザーが入力したコンテンツ（テキスト、画像、コード等）がAIによって生成されたものかどうかを判定し、
その確信度とともに結果を返すWebアプリケーション。

---

## 2. 技術アーキテクチャ設計方針

### 2.1 全体構成

```
[ユーザー]
    |
    v
[フロントエンド (SPA)]
    |  REST API / WebSocket
    v
[APIゲートウェイ / リバースプロキシ (Nginx)]
    |
    v
[バックエンド API サーバー]
    |
    +-- [判定エンジン (Detection Engine)]
    |       |
    |       +-- テキスト判定モジュール
    |       +-- 画像判定モジュール
    |       +-- コード判定モジュール
    |       +-- 統合スコアリング
    |
    +-- [非同期タスクキュー (Celery + Redis)]
    |       |
    |       +-- 重い判定処理のオフロード
    |       +-- バッチ処理
    |
    +-- [データベース (PostgreSQL)]
    |       |
    |       +-- ユーザー情報
    |       +-- 判定履歴
    |       +-- フィードバックデータ
    |
    +-- [キャッシュ (Redis)]
    |       |
    |       +-- 判定結果キャッシュ
    |       +-- セッション管理
    |
    +-- [オブジェクトストレージ (S3互換)]
            |
            +-- アップロードファイル保存
            +-- MLモデルファイル
```

### 2.2 設計原則

1. **マイクロサービス的モジュール構成**: MVP段階ではモノリスだが、判定エンジンは独立したモジュールとして設計し、後からサービス分離可能にする
2. **非同期処理**: 画像判定やバッチ処理など重い処理はタスクキューでオフロード
3. **拡張性**: 新しい判定手法やコンテンツ種別を追加する際にプラグイン的に差し込める設計
4. **API-First**: フロントエンドとバックエンドを完全分離し、将来的にサードパーティAPI提供も視野に入れる

## 4. AI生成物判定の技術的アプローチ

### 4.1 テキスト判定

#### A. 統計的特徴量分析
- **パープレキシティ分析**: AI生成テキストは人間の文章よりパープレキシティが低い傾向。言語モデルを使ってトークンごとのパープレキシティを計算し、分布を分析する
- **バースティネス (Burstiness)**: 人間の文章は文の長さや複雑さにばらつきがある。AI生成テキストはより均一な傾向があるため、文ごとのパープレキシティの分散を特徴量とする
- **エントロピー分析**: トークン分布のエントロピーを計測。AI生成テキストは特定のパターンに偏りやすい
- **繰り返しパターン**: n-gramの出現頻度、語彙の多様性 (TTR: Type-Token Ratio) を分析

#### B. ML分類器
- **RoBERTa ベースの分類器**: OpenAI の GPT-2 Output Detector を起点に、最新のAIモデル出力でファインチューニング
- **マルチモデル対応**: GPT-4, Claude, Gemini, Llama 等、複数のAIモデルの出力パターンを学習
- **アンサンブル手法**: 複数の分類器の結果を統合してロバスト性を向上

#### C. 電子透かし (Watermark) 検出
- **既知の透かしスキーム検出**: 各AIプロバイダが埋め込む透かし（例: OpenAI の C2PA メタデータ、Google SynthID のテキスト透かし）を検出
- **統計的透かし検出**: トークン選択の偏りパターンからの透かし推定

#### D. ゼロショット検出
- **DetectGPT方式**: テキストの対数確率に微小摂動を加え、その変化パターンからAI生成かどうかを判定（モデルの確率曲面の曲率を利用）
- **DNA-GPT方式**: テキストの続きを複数回生成させ、元テキストとの類似度パターンで判定

### 4.2 画像判定

#### A. メタデータ解析
- **EXIF / C2PA メタデータ**: AI生成画像に付与されるメタデータの有無と内容を解析
- **Content Credentials**: Adobe Content Authenticity Initiative (CAI) 準拠のメタデータ検出

#### B. 周波数領域分析
- **フーリエ変換 (FFT)**: AI生成画像はGANやDiffusionモデル特有の周波数パターンを持つ。高周波成分の分布を分析
- **DCT分析**: 離散コサイン変換による周波数特性の分析

#### C. CNN分類器
- **事前学習済みモデル**: AI生成画像と実写画像を判別するCNNモデル
- **GAN特徴検出**: GANが生成する画像特有のアーティファクト（例: チェッカーボードパターン）を検出
- **Diffusion特徴検出**: Stable Diffusion, DALL-E, Midjourney 等の出力特性を学習

#### D. SynthID検出
- **Google SynthID**: Googleが提供する電子透かし技術への対応

### 4.3 コード判定

- **コーディングスタイル分析**: 変数命名の一貫性、コメントの付け方、関数の長さの分布など
- **パターンマッチング**: AI特有のコード生成パターン（定型的なエラーハンドリング、過剰なコメント等）
- **AST (抽象構文木) 分析**: コードの構造的特徴量を抽出して分類

### 4.4 統合スコアリング

```
最終スコア = w1 * 統計分析スコア + w2 * ML分類スコア + w3 * 透かし検出スコア
```

- 各手法のスコアを正規化して0.0〜1.0の範囲に統一
- 重みは検証データでの精度に基づいて最適化
- 閾値ごとに「AI生成の可能性: 高/中/低」のラベルを付与
- 判定根拠（どの特徴が検出されたか）を可視化して返却

## 5. MVP実装の機能と技術的実現可能性

### 5.1 MVPスコープ

| 機能 | 優先度 | 実現可能性 | 備考 |
|------|--------|------------|------|
| テキスト判定 (日本語/英語) | 必須 | 高 | 既存モデル + ファインチューニングで実現可能 |
| 判定結果の可視化 | 必須 | 高 | フロントエンドで実装、パープレキシティのヒートマップ等 |
| ユーザー認証 | 必須 | 高 | NextAuth.js / OAuth 2.0 で実装 |
| 判定履歴の保存 | 必須 | 高 | DB保存、シンプルなCRUD |
| API提供 (REST) | 必須 | 高 | FastAPI の自動ドキュメントを活用 |
| 画像判定 (基本) | 望ましい | 中 | メタデータ解析 + 基本的CNN判定は実現可能。精度向上には追加学習が必要 |
| バッチ処理 | 望ましい | 高 | Celery で実装可能 |
| フィードバック機能 | 望ましい | 高 | ユーザーの正誤報告を収集し、モデル改善に活用 |
| コード判定 | 将来 | 中 | ASTベースの分析は可能だが、精度が課題 |
| リアルタイム判定 | 将来 | 中 | WebSocket対応、入力中の逐次判定 |

```
MVP構成:
- Next.js フロントエンド (Vercel にデプロイ可能)
```

## 6. 技術的リスクと課題

### 6.1 判定精度に関するリスク

| リスク | 影響度 | 発生確率 | 対策 |
|--------|--------|----------|------|
| AIモデルの進化で検出が困難になる | 高 | 高 | 継続的なモデル更新パイプライン構築、フィードバックループ |
| 日本語テキストの判定精度が低い | 高 | 中 | 日本語データセットでのファインチューニング、日本語固有の言語特徴量追加 |
| パラフレーズによる検出回避 | 中 | 高 | 複数の検出手法のアンサンブルで耐性向上 |
| 人間とAIの共同作成物の判定が曖昧 | 中 | 高 | 部分的AI利用率の推定、文単位の判定を実装 |

### 6.2 技術的課題

| 課題 | 詳細 | 対応方針 |
|------|------|----------|
| GPU推論コスト | MLモデルの推論にはGPUが必要で、コストが高い | ONNX Runtime での最適化、バッチ推論、キャッシュ活用でコスト削減 |
| レイテンシ | 複数の判定手法を実行すると応答時間が長くなる | 軽量手法を先行実行し即時結果を返し、重い手法は非同期で後から更新 |
| モデルサイズ | Transformerモデルは数GBに達する | 量子化 (INT8/INT4)、蒸留モデルの活用 |
| データセット | 最新AIモデルの出力データ収集が必要 | 主要AIサービスのAPIを利用してデータ収集パイプラインを構築 |
| 偽陽性/偽陰性 | 誤判定による信頼性低下 | 確信度とともに結果を返す設計、閾値の調整機能 |

### 6.3 法的・倫理的リスク

| リスク | 対応 |
|--------|------|
| プライバシー: ユーザーが入力したテキストの取り扱い | 判定後のデータ保持ポリシーを明確化、オプトイン方式でのデータ利用 |
| 著作権: 判定のためにAIモデルの出力を収集する行為 | 法務部と連携して適法性を確認 |
| 誤判定の責任: AI生成と誤判定された場合の影響 | 免責事項の明示、判定結果は「参考情報」として提供 |

### 6.4 運用リスク

| リスク | 対応 |
|--------|------|
| トラフィック急増 | オートスケーリング設定、レート制限の実装 |
| モデルのドリフト | 定期的な精度検証、A/Bテスト基盤の構築 |
| セキュリティ | 入力バリデーション徹底、ファイルアップロードのサニタイズ、WAF導入 |
