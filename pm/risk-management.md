## 1. 技術的リスク

### R-T01: 判定精度の不足
| 項目 | 内容 |
|------|------|
| リスクレベル | **高** |
| 発生確率 | 中 |
| 影響度 | 高 |
| 説明 | AI成果物の品質判定において、人間の判定と十分に一致しない可能性がある。特にハルシネーション検出や文脈依存の品質判断は技術的に難度が高い |
| 対策 | (1) MVP段階では判定対象をテキストに限定し、精度検証を優先する (2) 人間のフィードバックを取り込む仕組みを初期から設計する (3) 判定結果を「確信度」付きで提示し、低確信度のものは人間レビューを促す |
| 担当 | 開発部 + PM室 |
| ステータス | 監視中 |

### R-T02: AI API依存リスク
| 項目 | 内容 |
|------|------|
| リスクレベル | **高** |
| 発生確率 | 中 |
| 影響度 | 高 |
| 説明 | 外部AI APIの仕様変更、料金改定、サービス停止により、判定エンジンが動作不能になるリスク |
| 対策 | (1) 判定エンジンをAPI非依存の抽象レイヤーで設計し、プロバイダー切り替えを容易にする (2) 複数のAPIプロバイダーに対応する設計とする (3) APIの利用状況・コストを監視する仕組みを導入 |
| 担当 | 開発部 |
| ステータス | 監視中 |

### R-T03: レイテンシ・パフォーマンス問題
| 項目 | 内容 |
|------|------|
| リスクレベル | **中** |
| 発生確率 | 中 |
| 影響度 | 中 |
| 説明 | 外部AI APIへのリクエストに依存するため、判定に想定以上の時間がかかり、KPI（1件5秒以内）を達成できない可能性 |
| 対策 | (1) 非同期処理を導入し、ユーザーは結果を待たずに他作業可能とする (2) キャッシュ機構で同一・類似入力の再判定を高速化 (3) 軽量な判定項目はローカルで処理し、重い判定のみAPI呼び出し |
| 担当 | 開発部 |
| ステータス | 監視中 |

### R-T04: テストデータの品質・量の確保
| 項目 | 内容 |
|------|------|
| リスクレベル | **中** |
| 発生確率 | 高 |
| 影響度 | 中 |
| 説明 | 判定精度を検証するための「正解データ」の作成に大きなコストがかかる。十分なデータが揃わないと精度評価が信頼できない |
| 対策 | (1) 初期は少量の高品質データセット(100件程度)を人手で作成 (2) 社内のAI活用事例から実データを収集する (3) 段階的にデータを拡充する計画を策定 |
| 担当 | PM室 + 開発部 |
| ステータス | 監視中 |

### R-T05: セキュリティ・データ漏洩リスク
| 項目 | 内容 |
|------|------|
| リスクレベル | **高** |
| 発生確率 | 低 |
| 影響度 | 極高 |
| 説明 | ユーザーが投入するAI成果物に機密情報が含まれる可能性がある。外部APIへの送信時に情報漏洩が発生するリスク |
| 対策 | (1) 入力データの外部API送信前にユーザーに明示的な確認を求める (2) データ暗号化（通信時・保存時）を徹底 (3) データ保持ポリシーを策定し、不要データの自動削除を実装 (4) セキュリティテストをPhase 3で実施 |
| 担当 | 開発部 + 法務・経理部 |
| ステータス | 監視中 |

## 2. ビジネスリスク

### R-B01: 市場ニーズとのミスマッチ
| 項目 | 内容 |
|------|------|
| リスクレベル | **高** |
| 発生確率 | 中 |
| 影響度 | 高 |
| 説明 | 「AIの成果物を判定する」ニーズが想定ほど強くない、または想定とは異なる形で求められている可能性 |
| 対策 | (1) Phase 0で市場調査を徹底し、ターゲットユーザーの実態を把握 (2) MVP段階で早期にユーザーフィードバックを取得 (3) ピボット可能な柔軟な設計にする |
| 担当 | マーケティング部 + PM室 |
| ステータス | 監視中 |

### R-B02: 競合プロダクトの先行・参入
| 項目 | 内容 |
|------|------|
| リスクレベル | **中** |
| 発生確率 | 高 |
| 影響度 | 中 |
| 説明 | AI品質評価は注目領域であり、大手テック企業や新興スタートアップが類似プロダクトをリリースする可能性が高い |
| 対策 | (1) 差別化要素（カスタマイズ性、日本語対応の高品質さ等）を明確にする (2) 開発スピードを優先し、MVPの早期投入を目指す (3) 継続的な競合分析を実施 |
| 担当 | マーケティング部 |
| ステータス | 監視中 |

### R-B03: AI API利用コストの増大
| 項目 | 内容 |
|------|------|
| リスクレベル | **中** |
| 発生確率 | 中 |
| 影響度 | 高 |
| 説明 | 外部AI APIの呼び出しコストが利用量に比例して増大し、ビジネスモデルとして成立しなくなるリスク |
| 対策 | (1) API呼び出し回数を最適化するアーキテクチャ設計 (2) 段階的な料金体系の設計（利用量に応じた課金） (3) コスト監視ダッシュボードの導入 (4) 将来的にはローカルモデルの活用も検討 |
| 担当 | 開発部 + 法務・経理部 |
| ステータス | 監視中 |

### R-B04: 法的責任・信頼性リスク
| 項目 | 内容 |
|------|------|
| リスクレベル | **中** |
| 発生確率 | 低 |
| 影響度 | 高 |
| 説明 | 判定結果を信頼したユーザーが、実際には品質の低いAI成果物を使用してしまった場合の責任問題。「判定した=品質保証した」と誤解されるリスク |
| 対策 | (1) 判定結果はあくまで「参考情報」であることを明示する免責事項の整備 (2) 判定の限界を正直に伝えるUI設計 (3) 利用規約に責任範囲を明記 |
| 担当 | 法務・経理部 + デザイン部 |
| ステータス | 監視中 |

### R-B05: スケジュール遅延リスク
| 項目 | 内容 |
|------|------|
| リスクレベル | **中** |
| 発生確率 | 中 |
| 影響度 | 中 |
| 説明 | 各部署の並行作業における依存関係や、技術的な想定外の問題により、スケジュールが遅延するリスク |
| 対策 | (1) クリティカルパスを明確化し、ボトルネックを先行して着手 (2) 週次の進捗確認で早期に遅延を検知 (3) 各フェーズに10-20%のバッファを確保 (4) スコープの柔軟な調整（優先度低の機能は後回し） |
| 担当 | PM室 |
| ステータス | 監視中 |
